# kwiry-search 0.6.0-beta.23

A failed search now says *why* it failed.

## Search failures name their cause

`query_execution_failed` was a catch-all. Every throw inside search collapsed into it and the thrown value was discarded, deliberately: an exception message can quote SQL, the query, or note text, none of which may enter a diagnostics report. The result was a report that recorded a failure but could say nothing about it, so a reported error could only be chased by trying to reproduce it by hand.

A failure now carries a classification drawn from a fixed set:

- `sqlite` — the database rejected the statement;
- `plan_rejected` — the bound execution plan was refused;
- `bounds_exceeded` — an internal bound was hit;
- `internal` — anything else.

The thrown value itself is still discarded. Only the classification travels, and it appears in the exported diagnostics as `failureCause` alongside the existing code and stage.

This is enough to say which half of the system failed without anyone sharing a vault, a query, or a raw log.

## What this does not change

No ranking, planning, extraction, or indexing behaviour changes in this release. Search results are identical to beta.22.

## Compatibility identities

- Worker protocol 12 → 13 (the error envelope gained one optional, closed-vocabulary field).

Unchanged: lexical query-plan schema 7, FTS5 match-plan schema 6, the `lexical-v1` profile, **cache schema 11**, cache image formats, source policy, source and extractor identities, chunking, and every ranking bound. **No reindex is required.**

## Known issues, unchanged from beta.22

- **Native and in-plugin ranking can disagree.** On an identical five-document corpus, the query `security te` returns the note named `Security Team` from the native engine but a different note from the in-plugin engine. The shared conformance corpus exists to keep the two aligned and does not currently cover this shape. Under investigation; an earlier guess that the minimum prefix length caused it was tested and disproved.
- Diagnostics still do not record which evidence tiers were planned or how many completions were kept. The failure classification above is the first half of closing that gap.
- Ranking remains a tier cascade rather than a single weighted score.

## Verification and publication boundary

Automated verification covers the complete plugin suite including a regression that injects a throw carrying SQL and a path, then asserts the classification survives while none of that text reaches the response; type checking; privacy validation; build output; and the existing evidence, smoke, licence, and package checks. The Rust core is untouched by this release.

Beta.23 does not amend `CONTRACT.md`. Tagging and publication require separate authorization after the immutable candidate gate succeeds.

## Install

After beta.23 is separately authorized and published, install or update through BRAT using repository `cybersader/kwiry`, or use the release archive produced by the protected release workflow.
