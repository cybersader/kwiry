# kwiry-search 0.6.0-beta.27

This release makes `lexical-v2` the default lexical relevance profile, adds fixed field controls, and keeps the same policy across the native daemon, the in-plugin FTS5-WASM backend, and OpenClast lexical search.

## Source identity can outrank body repetition

Lexical-v2 ranks bounded, field-aware evidence in shared Rust. Strong source-identity evidence from filenames, titles, and aliases can now outrank a body-only phrase match. Headings, tags, and body evidence remain part of the closed scorecard, and final ordering stays deterministic.

The in-plugin backend executes fixed SQL lanes declared by Rust, retains bounded authorized candidate proofs, and returns those proofs to Rust for final ordering. TypeScript validates and binds the closed execution plan; it does not parse public query controls or define relevance weights.

`lexical-v1` remains an explicit compatibility identity. There is no silent profile fallback, mode fallback, or backend switch.

## Fixed field controls

Lexical queries now support two leading controls:

- `in:<field>` strictly scopes lexical matching;
- `><field>` applies one fixed bounded preference.

Supported public fields are `name`, `filename`, `title`, `alias`, `heading`, `tag`, and `body`. Examples:

- `in:name Vendor7 meeting`
- `>title Vendor7 meeting`
- `in:name >title Vendor7 meeting`

Only one scope and one preference are allowed. Unknown, duplicate, incompatible, or empty controls fail with the fixed `invalid_field_control` category. Arbitrary numeric boosts and user-defined weights are not accepted.

Mode behavior is explicit:

- Lexical supports strict scope and preference.
- Hybrid supports preference on its lexical leg. Its semantic leg receives only the stripped query text.
- Hybrid rejects strict scope.
- Semantic rejects all lexical field controls.

Field-control tokens are not excerpt-highlight terms.

## Search-modal disclosure

The compact search context bar now includes an accessible `Field syntax` control. It explains the supported syntax and mode restrictions without adding a third permanent status row.

After a successful policy-bearing search, the modal displays only active controls, such as `Scope · Name` or `Prefer · Body`. A new query or requested-mode change clears the old label immediately so stale policy facts are never presented as current.

Invalid controls and an older daemon that cannot disclose beta.27 policy produce fixed inline guidance without exposing query text or raw backend details.

## Daemon and OpenClast policy facts

The frozen search response body remains unchanged. A beta.27 daemon discloses effective lexical policy through three closed response headers:

- `x-kwiry-lexical-profile`
- `x-kwiry-field-scope`
- `x-kwiry-field-emphasis`

Ordinary searches remain compatible with an older daemon that does not return these headers. A control-bearing query requires a beta.27-compatible daemon and fails explicitly rather than silently stripping the control.

Authentication and OpenClast capability checks still precede retrieval. OpenClast remains lexical-only and resource-qualified; lexical-v2 does not widen authorized candidate access.

## Compatibility

This release changes transient query and Worker contracts but does not change persisted source or index identity:

- Worker protocol advances from 13 to 14 to carry effective query-policy facts;
- lexical query-plan schema advances to 8;
- portable FTS5 execution-plan schema advances to 7;
- plugin cache schema remains 12;
- source-preparation schema remains 10;
- source identities, chunk identities, extraction behavior, and indexed field storage are unchanged.

No forced reindex is required. Existing disposable native and in-plugin indexes remain compatible because neither persisted index schema nor extraction identity changes.

## Verification and publication boundary

Automated coverage includes native and portable lexical-v2 ordering, bounded preference reversal, strict field scope, deterministic and fail-closed ranking bounds, Worker policy validation, stripped highlight terms, daemon policy headers, hybrid/semantic control rejection, OpenClast authorization, privacy-safe errors, and modal/status-rail preservation.

The real Obsidian WebDriver/X11 candidate gate remains part of the protected release workflow. BRAT publication still requires the immutable candidate handoff accepted by the publisher workflow.

## Install

After the protected candidate and publisher workflows complete, install or update through BRAT using repository `cybersader/kwiry`, or use the release archive attached to `0.6.0-beta.27`.
