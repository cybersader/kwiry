# kwiry-search 0.6.0-beta.21

Beta.21 fixes the reason an abbreviation stops working once the abbreviation itself appears anywhere in the vault. Typing `vuln meetings` could fail to surface a note named `Vulnerability-Meetings`, and no amount of re-ranking helped, because the note was never a candidate.

## Prefix assistance no longer depends on the stem existing elsewhere

Bounded prefix expansion was requested only when the typed stem had no matches at all. That asked whether the stem exists *anywhere in the vault*, not whether it is useful for the query being typed. One standalone `vuln` — a tag, a path segment, prose shorthand, one unrelated note — made `vuln` "supported", so no `vuln…` completions were collected, no prefix stages were planned, and the remaining ladder demanded the literal token `vuln`. A note whose filename tokenizes to `vulnerability` + `meetings` cannot supply that.

Eligibility is now a property of the term itself — an optional analyzed term, long enough, with at least one genuinely longer completion in the vault — and not of some unrelated document. The typed stem is itself one of its own completions, so an exact match remains available as one alternative in the expansion rather than as a precondition.

A term that expands to nothing but itself is left alone: the all-terms tier already requires it exactly, so no prefix stages are planned and complete queries behave exactly as before.

Because a term may now be both directly supported and expanded, the two prefix stages require the relaxed terms **minus** the terms they expand. Requiring a term exactly *and* expanding it in the same stage would defeat the expansion, and a plan that does both is refused as `invalid_query_plan`. Identifier anchors are never expanded and remain strictly required.

## What beta.19 and beta.20 did and did not do

Beta.19 ordered bounded prefix evidence ahead of broad partial coverage. Beta.20 changed which completions fill the bounded budget and split prefix evidence into a metadata-scoped stage and a text stage. Both operate *after* assistance has been requested. In the case above assistance was never requested, so neither release affected it. Beta.21 is what makes those two improvements reachable for an abbreviation whose stem already exists.

## Index status counter

The in-flight count in the Obsidian status bar changed width as it crossed 9 → 10, resizing the status bar item and shoving neighbouring items sideways. The figure-space padding that prevents this existed but had been applied only to the search modal's status rail. It now lives where the count is written, so both surfaces stay stable.

## Compatibility identities

This is a correctness repair within the existing `lexical-v1` profile. The plan shape changes, so two internal schema versions move with the code that reads them:

- lexical query-plan schema 5 → 6;
- FTS5 match-plan schema 4 → 5 (the term-support probe now also carries the analyzed stem).

Unchanged: Worker protocol 12, **cache schema 11**, cache image formats, source policy, source and extractor identities, chunking, candidate and prefix bounds, and the closed diagnostics and privacy boundary. **No reindex is required** — the normal beta version update applies.

## Cost

Completion probes now run for every eligible term rather than only for terms with no matches, within the existing bound of eight probed terms, a 256-entry scan window, and 16 kept completions per term. Identifier anchors are skipped. Terms that expand only to themselves plan no additional stages.

## Known limit

The 16-completion budget still exists. A long target behind a very common short stem can still fall outside the kept set unless it appears in a filename, stem, alias, or title. This is bounded prefix assistance, not general fuzzy or typo-tolerant matching.

## Source-read field report boundary

The outstanding report that reaches `source_read_capacity` with inventory complete and no documents acknowledged remains a separate investigation. Beta.21 does not weaken abandoned-read protection or claim a speculative scheduler fix.

## Verification and publication boundary

Automated verification covers Rust planning, native search, and expansion eligibility; the abbreviation A/B fixture that fails on beta.20; D5C tier monotonicity; Rust and WASM byte parity across both portable adapters; the shared lexical conformance corpus; direct FTS5 execution; the exact generated production Worker; type checking; privacy validation; build output; and the existing evidence, smoke, licence, and package checks.

Beta.21 does not amend `CONTRACT.md`. Tagging and publication require separate authorization after the immutable candidate gate succeeds.

## Install

After beta.21 is separately authorized and published, install or update through BRAT using repository `cybersader/kwiry`, or use the release archive produced by the protected release workflow.
