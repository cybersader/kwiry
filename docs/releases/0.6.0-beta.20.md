# kwiry-search 0.6.0-beta.20

Beta.19 moved bounded prefix evidence ahead of broad partial coverage, but an incomplete multi-word search could still miss the note it was clearly aiming at. Beta.20 fixes the remaining cause, which is candidate selection rather than ranking, and makes title and filename prefix evidence categorically stronger than body text.

## Which expansions the prefix budget keeps

When a typed word is incomplete, both engines walk the vault's own vocabulary for real words that extend it and keep a bounded number of them. That budget is unchanged at 16 terms per typed word. What changed is which 16.

Previously the budget was filled lexicographically. In a real vault a stem such as `adop` has more than 16 alphabetically earlier neighbours — `adopt`, `adoptable`, `adopted`, `adoptee`, `adopter`, `adopting` and their plurals — so `adoption` was never a candidate in any stage, and no amount of re-weighting could rank a term that was never selected. Typing one more letter narrowed the walk enough for the term to survive, which is exactly the reported behaviour.

Beta.20 examines a wider bounded window of the vocabulary and then spends the same 16-term budget on the expansions a person is actually navigating toward:

1. terms that occur in a filename, stem, alias, or title;
2. then the terms closest in length to what was typed;
3. then lexicographic order.

Both the native engine and the in-plugin engine apply the identical rule and still return the expansions as a canonical set, so plans stay comparable across engines.

Document frequency is deliberately not part of the ordering. The two engines count documents differently by construction, and ranking on those numbers would break the native and portable parity the shared conformance corpus enforces.

## Title prefix evidence before body prefix evidence

Bounded prefix evidence is now emitted as an ordered pair of stages: a metadata-scoped stage over filename, stem, aliases, and title, followed by the existing stage over all searchable text. The full ladder is:

1. exact metadata;
2. exact phrase;
3. all terms;
4. prefix — metadata fields;
5. prefix — searchable text;
6. partial coverage.

Because both executors preserve stage order and stop when the visible result window is full, a title or filename prefix hit now precedes any body-text prefix hit categorically, rather than depending on a BM25 field-weight blend that a rare body term can win. The pair is always emitted together; a plan carrying only one half is refused as `invalid_query_plan`.

## Link insertion is decided by the backend

Inserting a link from a search result was refused for every non-Markdown result. That was a client-side assumption, and it is now a declared capability of the source-format registry in the Rust core, mirrored into the plugin and enforced by a parity test so admitting a format cannot silently skip the decision.

- A note link works for any indexed result, whatever its format. Every indexed source is a file in the vault and can be linked to by name.
- A section link is offered only where a matched heading is genuinely a link anchor, which today means Markdown. A heading extracted from a PDF page, a DOCX outline, or a workbook sheet names a region of the extraction rather than a destination a `#` link can reach.

Inserting a link also leaves the caret after the inserted link instead of in front of it, so typing continues the sentence.

## Format parity fix

The in-plugin prefix vocabulary scan omitted the `tags` column that the native prefix field group has always included. The two engines now scan the same fields.

## Compatibility identities

This remains the `lexical-v1` profile; it repairs the implementation of the existing bounded evidence ladder rather than introducing a selectable retrieval profile. The plan shape did change, so two internal schema versions move together with the code that reads them:

- lexical query-plan schema 4 → 5 (new bound, new field group, new stage kind);
- FTS5 match-plan schema 3 → 4 (new stage plan id, new probe bound).

Unchanged: Worker protocol 12, cache schema 11 and cache image formats, source policy, source and extractor identities, chunking, candidate and prefix bounds, and the closed diagnostics and privacy boundary. Plugin-version cache compatibility remains strict, so the normal beta update may still require a rebuild.

## Known limit

The 16-term budget still exists. A long target sitting behind a very common short stem — `conf` reaching `configuration` — can still fall outside the kept set unless it appears in a filename, stem, alias, or title. Metadata presence is what rescues the realistic case. This is bounded prefix assistance, not general fuzzy or typo-tolerant matching.

## Source-read field report boundary

The outstanding beta.18 report that reaches `source_read_capacity` with inventory complete and no documents acknowledged is still a separate investigation. It does not contain the earlier operation that occupied the bounded read slots, and beta.20 neither weakens abandoned-read protection nor claims a speculative scheduler fix.

## Verification and publication boundary

Automated verification covers Rust planning, native search, and expansion selection; D5C tier monotonicity; Rust and WASM byte parity; the shared lexical conformance corpus; direct FTS5 execution and candidate-window traces; the exact generated production Worker, including refusal of a broken prefix pair; the format link-capability mirror; link insertion behaviour; type checking; privacy validation; build output; and the existing evidence, smoke, licence, and package checks.

Beta.20 does not amend `CONTRACT.md`. Tagging and publication require separate authorization after the immutable candidate gate succeeds.

## Install

After beta.20 is separately authorized and published, install or update through BRAT using repository `cybersader/kwiry`, or use the release archive produced by the protected release workflow.
