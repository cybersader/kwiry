# kwiry-search 0.6.0-beta.12

A pre-release of the Kwiry Search Obsidian plugin and the `kwiry` daemon. Two things
decide whether you should take this update: it costs you one rebuild, and it corrects
dependency licence notices that were wrong in the copy you already have.

## 1. First launch rebuilds your index, once

This release invalidates every stored index and cache. There is no migration.

What that looks like:

- **Obsidian plugin** — the cached index from beta.11 cannot be restored. The plugin
  rebuilds from your vault once. The cost is proportional to vault size and is paid a
  single time.
- **`kwiry serve`** — the stored generation is refused, the reason is printed, and every
  source is reindexed. The desktop daemon keeps answering requests with an explicit
  `index_building` response while it rebuilds rather than serving stale rows.
- **`kwiry search`** — refuses until you run `kwiry index`.
- **Semantic vectors** (if enabled) are re-embedded source by source, not wiped in bulk.

Why it cannot be migrated: every indexed file now records a fingerprint of *how* it was
extracted — the format, the compiled extraction profile, and the extractor's declared
version. Rows written by earlier builds carry no such fingerprint, and one cannot be
derived without re-reading the file. A missing fingerprint is deliberately treated as a
refusal, never as a match, because the alternative is silently serving rows built by an
extractor you can no longer identify.

Version gates that moved: manifest 4 → 5, plugin cache schema 9 → 10, worker protocol
10 → 11, plus a new format-identity schema at version 1.

Rolling back to beta.11 is supported and will not corrupt anything, but it requires a
rebuild in that direction too.

## 2. Licensing correction — this affects the build you already installed

`Rust-DEPENDENCY-LICENSES.md` ships inside the plugin package, so every beta.11 install
carries a copy. That copy was wrong in five places:

- **Three MIT crates compiled into the plugin's WebAssembly had no notice at all**:
  `lopdf 0.44.0`, `nom 8.0.0`, and `ecb 0.2.0`.
- **Two more had been swapped with each other.** The `rawzip 0.5.1` section reproduced
  quick-xml's MIT text, including quick-xml's copyright holder, and the `quick-xml 0.41.0`
  section reproduced rawzip's. Each now carries its own: quick-xml's names
  `Copyright (c) 2016 Johann Tuffe`, and rawzip's upstream licence genuinely names no
  holder, so none is invented.

All five verbatim notices are corrected here, and every MIT notice in the bundle has been
diffed against that crate's own upstream licence file as vendored by Cargo. The file's
"Release license selections" summary — which had drifted to omit 29 of the 95 shipped
crates — is regenerated from the same inventory that validates the graph. Both pinned
dependency inventories record the corrected bundle's digest (95 crates each).

Two checks changed, because the ones that existed could not see this. Each MIT notice
*body* is now pinned by digest, holder-less notices are recorded as holder-less so nobody
"fixes" one with a borrowed line, and no two crates may share a notice body — the previous
check asserted only that the string `<name> <version>` occurred somewhere in the bundle,
which a section heading satisfies by itself, which is exactly why a section containing
another crate's licence passed it. The roll-up is now re-derived from the inventory rather
than maintained by hand. Both run in the required CI workflow that publication already
gates on, along with the dependency licence validator that previously ran only in a branch
workflow.

If you redistribute, vendor, or audit a beta.11 build, this alone is a reason to upgrade.

## What is better: changing a format no longer throws the whole index away

Previously, the set of enabled formats and the extraction policy were part of the index's
identity. Enabling DOCX, or moving PDF from the portable extractor to the enhanced one,
invalidated the entire index and re-read every file in the vault — including Markdown
files that were completely unaffected by the change.

Identity is now recorded per format. When one format's extraction identity moves, only
that format's sources are evicted and re-read; every other row is reused.

Measured:

- In the daemon's tests, a two-source vault spanning two formats re-read **exactly one
  source** after one format's identity moved.
- In the plugin's tests, **one of three** cached rows was evicted and two were reused,
  and the first query after restore could no longer see the evicted row.
- On one real vault, moving PDF from the portable to the enhanced extractor re-read
  **1 source and 1011 bytes**, where beta.11 refused the whole generation and re-read all
  six. This is a single field measurement on one vault, reported as what happened — not a
  performance target and not a figure you should expect to reproduce.

Separately, **toggling a source format in Obsidian settings no longer discards the cache
at all.** The enabled-format set was removed from the cache identity entirely. It is now
configuration applied at restore time as a projection: turning a format off hides its
sources, and turning it back on re-reads only those sources.

The status line is honest about what is happening rather than saying "rebuilding". A
partial reuse now reports, for example:

```
Cached index searchable; reindexing DOCX and PDF sources and removed Canvas sources…
```

The two reasons are kept apart on purpose: sources with a stale extraction identity will
be re-read; sources belonging to a disabled format will not. The daemon prints the
equivalent line on both the whole-generation and per-format paths — previously a
whole-generation discard happened silently.

One caveat worth stating plainly: **no extractor version has actually been bumped yet.**
Every format's extractor version is still 1. The per-format machinery has been proven by
profile differences (portable versus enhanced PDF) and by tests, not yet by a real
behaviour change shipping through it.

## Also fixed

**Excalidraw files could not be indexed by the plugin at all, in beta.8 through beta.11.**
The cache schema's format constraint omitted `excalidraw` while the format was enabled by
default, so the row could not be inserted. Blast radius is narrower than it sounds: the
Excalidraw plugin writes `.excalidraw.md` by default and classification is
last-extension-wins, so those files were indexed as Markdown and were never affected. Only
raw `.excalidraw` files — the legacy export form — hit the constraint. Fixed here, with a
regression test, riding the same cache schema bump the identity column needed.

**The DOCX dependency guard now checks the property it cares about** — that no C zlib
implementation enters the WebAssembly graph — instead of asserting an exact feature list
that a legitimate dependency graph could no longer satisfy.

**`kwiry-search.zip` now carries the licence with the binary.** The archive is advertised
as the install-by-hand path, but it held only `main.js`, `manifest.json`, and `styles.css`,
so anyone who took just the zip received GPL-3.0-only software with no licence text and no
third-party notices — those sat beside it as separate release assets. It now also contains
`LICENSE`, `THIRD_PARTY_NOTICES.md`, `Apache-2.0.txt`, `Emscripten-LICENSE.txt`, and
`Rust-DEPENDENCY-LICENSES.md`. Obsidian ignores the extra files; the release checksums and
the automation evidence are deliberately left out.

**Editing your notes no longer changes how unrelated notes rank.** This shipped as a known
issue in earlier drafts of these notes — "BM25 score drift after a partial reindex" — and
it is fixed rather than documented. It had three independent causes, and removing any two
of them left search still answering differently depending on how the index had been built:

- Tantivy does not remove a deleted document; it marks it dead and leaves its postings,
  its term-dictionary entries and its token counts in the segment. Every BM25 corpus
  statistic is read off those segments, so a removed note kept voting on the ranking of
  the notes that remain. Publication now rewrites exactly the segments carrying deletions,
  and an index inherited from an earlier build is repaired before it is served rather than
  after the vault next changes.
- Rewriting those segments is the one path on which tantivy cannot preserve a field's
  exact token total — it re-derives it from quantised field lengths — so the repair itself
  left the index reporting a collection length a few percent under what a rebuild reports.
  Scoring now derives that length from the live documents instead of from a figure recorded
  when the segment was written, which is the only formulation both build paths can agree on.
- The prefix ladder spent its expansion budget per dictionary entry visited rather than per
  distinct term, so a term recorded in three segments cost three times what the same term
  costs after a merge, and an incrementally maintained index expanded a prefix to a
  different set of terms than a rebuild did.

Together these made the difference larger than "slight" and larger than "ordering": because
each stage of the evidence ladder is a bounded top-k, a perturbed score changes which
candidates reach the next stage, so a document a full rebuild returns could be missing from
an incremental index's results outright. A 200-note corpus of ordinary-length notes,
reindexed after twenty edits, returned a different answer set from a rebuild of the same
bytes. It now returns the same documents in the same order, held there by a regression test
whose corpus fails loudly if it ever drifts short enough to stop exercising the defect.
A full reindex is no longer needed for this, and no longer changes the answer.

## Known issues

- **`kwiry search` never benefits from per-format reuse.** The read-only CLI path holds no
  writer lock and therefore cannot evict rows, so when any format's identity has moved its
  only honest option is to refuse the whole index and ask you to run `kwiry index` — even
  for formats whose identity is intact. Only `kwiry serve` and the Obsidian plugin do
  partial reuse. This is a deliberate consequence of the design, not a defect.
- **An extractor can change without changing its identity.** The fingerprint covers the
  format name, the extraction profile, and a declared extractor version. Nothing detects an
  extractor whose implementation changed while its profile name and version stayed the
  same; the only defence is discipline plus a test that pins the shipped identities. If that
  discipline slips, stale rows would be reused silently.
- **The notice bundle is pinned against Cargo's vendored sources by hand.** The digests
  that now guard each MIT notice were derived by diffing the bundle against the upstream
  licence files, but nothing re-derives them automatically at build time. Bumping an MIT
  crate fails the check — which is the point — and whoever re-pins it must diff the new
  upstream file rather than paste in whatever the bundle happens to say.

## Formats

Enabled by default: Markdown, plain text, Base, Canvas, DOCX, Excalidraw.
**PDF is supported but off by default** — enable it in settings if you want it, and expect
those sources to be read on the next index.

## Install

Install or update via BRAT, or copy `main.js`, `manifest.json`, and `styles.css` into the
plugin directory — `kwiry-search.zip` holds those three together with the licence and the
third-party notices. Licensed GPL-3.0-only; corresponding source ships with the release.
