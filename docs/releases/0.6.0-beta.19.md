# kwiry-search 0.6.0-beta.19

Beta.19 corrects the lexical evidence order used for incomplete multi-word searches. A title or filename whose trailing token matches the typed prefix can now enter the bounded result window before broader matches that satisfy only the already-complete terms.

## Prefix evidence before partial coverage

The Rust-owned evidence ladder is now:

1. exact metadata;
2. exact phrase;
3. all terms;
4. bounded prefix;
5. partial coverage.

Previously, partial coverage ran before prefix evidence. Because native and in-plugin search both preserve stage order and stop when the requested result window is full, enough broad partial matches could prevent the more specific prefix stage from running at all. That made an incomplete query such as an invented two-word title prefix require the final word to be typed in full.

Beta.19 moves only the bounded prefix stage ahead of partial coverage. Exact metadata, exact phrases, and complete all-term matches retain precedence. Prefix assistance remains limited to the existing minimum length, term count, expansion count, UTF-8 term size, per-stage candidate count, and total candidate count.

## Native, WASM, and Worker parity

The canonical order is owned by `kwiry-core` and mirrored at the TypeScript validation boundary. Native Tantivy, the portable Rust/WASM adapter, in-plugin FTS5, and the exact generated production Worker now share the same order.

Regression coverage includes a generated result window filled by partial-only decoys and one title/filename prefix-specific hit. The prefix hit must remain visible before the partial results, while tampering a finalized plan back to partial-before-prefix is rejected as `invalid_query_plan`.

A separate invented all-uppercase alphabetic term is also tested as ordinary analyzed lexical content with only Markdown enabled. Source-format settings continue to decide what is indexed; they do not reinterpret terms or extensions as query operators.

## Compatibility identities

This is a correctness repair within the existing `lexical-v1` profile. Beta.19 does not change:

- lexical query-plan schema 4;
- FTS5 match-plan schema 3;
- Worker protocol 12;
- cache schema 11 or cache image formats;
- source policy, source identities, extractor identities, or chunking;
- candidate and prefix bounds;
- the closed diagnostics and privacy boundary.

Plugin-version cache compatibility remains strict, so the normal beta version update may still require a rebuild.

## Source-read field report boundary

The latest sanitized beta.18 report records a retry that reached `source_read_capacity` with inventory complete and no documents acknowledged. It does not contain the earlier operation that occupied the bounded read slots. Beta.19 does not weaken abandoned-read protection or claim a speculative source-read scheduler fix; that field issue remains separate until its first causal stall is reproduced or captured.
