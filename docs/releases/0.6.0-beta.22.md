# kwiry-search 0.6.0-beta.22

A note *named* for what you typed now outranks a note that merely mentions it.

## Name evidence before body evidence

Typing `vuln meet` could return a note whose body prose happened to contain both typed fragments ahead of the note actually named `Vulnerability-Meetings`. Beta.21 made the expansion from `vuln` to `vulnerability` work; this release makes the resulting match win.

The cause was tier order. Evidence tiers execute in sequence and fill the visible result window, so a later tier never competes on score with an earlier one — field weights only apply *within* a tier. The all-terms tier, which matches the literal typed tokens in **any** field including body content, ran ahead of the name-scoped prefix tier. A passing sentence therefore beat a filename.

The ladder is now:

1. exact metadata;
2. exact phrase;
3. **prefix — filename, stem, aliases, title**;
4. all terms;
5. prefix — all searchable text;
6. partial coverage.

The bounded prefix pair now straddles the all-terms tier rather than sitting below it: name evidence above, body evidence below. A plan carrying only one half is still refused as `invalid_query_plan`.

An exact phrase match is unchanged and still ranks above both, because a body passage containing your exact typed phrase is genuinely strong evidence.

## What this does not change

Queries with no incomplete word are unaffected: with no prefix tiers planned, the ladder is exactly as before. Expansion selection, the bounded budgets, and prefix eligibility are all untouched from beta.21.

## Compatibility identities

A correctness repair within the existing `lexical-v1` profile. The plan shape changes, so two internal schema versions move with the code that reads them:

- lexical query-plan schema 6 → 7;
- FTS5 match-plan schema 5 → 6.

Unchanged: Worker protocol 12, **cache schema 11**, cache image formats, source policy, source and extractor identities, chunking, candidate and prefix bounds, and the closed diagnostics and privacy boundary. **No reindex is required.**

## Known limits

- **Diagnostics still cannot explain a ranking result.** Search records carry a result count and a generic failure code, but not which tiers were planned or how many completions were kept. That gap is why a reported bad ranking currently has to be reproduced by hand rather than read from a report. Closing it needs a Worker protocol change and is deliberately not bundled here.
- The 16-completion budget still applies. A long target behind a very common short stem can fall outside the kept set unless it appears in a filename, stem, alias, or title.
- Ranking remains a tier cascade rather than a single weighted score. Moving to a weighted model — combining field weight, match completeness, and optionally recency — is recorded as a research topic rather than attempted here.

## Verification and publication boundary

Automated verification covers Rust planning and native search, including a regression that fails on beta.21's ladder; D5C tier monotonicity; both portable adapters at byte parity; the shared lexical conformance corpus; direct FTS5 execution; the exact generated production Worker; type checking; privacy validation; build output; and the existing evidence, smoke, licence, and package checks.

Beta.22 does not amend `CONTRACT.md`. Tagging and publication require separate authorization after the immutable candidate gate succeeds.
