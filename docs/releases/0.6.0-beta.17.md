# kwiry-search 0.6.0-beta.17

Beta.17 addresses a large-vault initial-build failure reported on Windows. With PDF disabled, Excel enabled, and 4,556 sources, beta.16 stopped at exactly 400 completed sources: the first 25-batch checkpoint boundary at the production batch size of 16.

## Large-vault initial builds

Healthy initial builds no longer pause every 25 acknowledged batches to export and persist a complete staging SQLite image. Those repeated whole-image exports grew with the index and ran under the same deadline as ordinary Worker requests, so a large Excel-enabled build could time out or lose its Worker at the first checkpoint.

Beta.17 lets the healthy build continue directly through commit. Existing initial-build checkpoints remain readable, and the controller retains bounded best-effort checkpoint opportunities when a build fails or the plugin shuts down. Completed-checkpoint cleanup is unchanged.

## Worker operation deadlines and ordering

Full-corpus Worker operations now have a bounded five-minute deadline:

- initial-build commit;
- complete-generation export and restore;
- initial-checkpoint restore;
- complete reconciliation planning.

Ordinary source batches, mutations, search, status, abort, checkpoint export, and disposal retain the ordinary request deadline. Host-side barriers hold requests submitted after a full-corpus operation until that operation completes, so an ordinary request does not consume its timeout while waiting behind compaction, export, restore, or reconciliation.

The RPC client also preserves the first terminal timeout, crash, or protocol failure. Later requests against the poisoned client report that original safe categorical cause instead of replacing it with `disposed`. Deliberate disposal remains nonrecoverable `disposed`.

## Bounded recovery and cache persistence

An uncertain final cache-export failure now enters the existing one-replacement Worker recovery path. If the replacement encounters the same uncertainty before cache persistence succeeds, the backend becomes unavailable rather than starting an endless replacement loop. A definitive cache-store failure remains a nonfatal durability issue: the current generation stays searchable and the Worker is not replaced.

## Compatibility identities

Beta.17 does not change the Worker protocol, cache schema, initial-checkpoint record or image format, checkpoint ordering, source policy, ranking identity, or extractor identities. Plugin-version cache compatibility remains strict; this hotfix does not weaken that policy, so an existing cache may still be rejected after the version update and rebuilt.

## Verification and acceptance boundary

The automated regression uses an in-memory 4,556-source vault shape with production batch size 16, Excel enabled, and PDF disabled. It proves that the build passes 400, acknowledges 285 source batches, performs no periodic checkpoint export, commits once, and reaches a searchable generation. Focused tests also cover long-operation deadlines, queue barriers, terminal-cause preservation, bounded Worker replacement, definitive cache-store failure, checkpoint restore, failure checkpointing, shutdown checkpointing, and completed-checkpoint cleanup without materializing a physical 4,556-file fixture.

Automated tests do not replace owner field acceptance. The decisive beta.17 check remains a Windows cold build with PDF off and Excel on across the reported 4,556-source vault, followed by search and reload/reconciliation checks. Beta.17 does not amend `CONTRACT.md`.
